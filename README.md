## 1. サービス概要

部屋の上面図をブラウザ上で自由に描き、座席を配置して着席状況をリアルタイムで管理できるWebアプリ。
まずは**勉強会・もくもく会・サークル活動などのカジュアルな集まり（toC）**を主な対象とし、「入室前に誰がどこにいるか」を一目で把握できるようにすることで、個人同士の合流のストレスをなくすことを目的とする。
紙の座席表・口頭確認・Slackでの「どこにいる？」といったやり取りを、URLを開くだけのシンプルなビジュアル操作に置き換える。
同じ「自由席で人の所在が変わる」という構造は飲食店やイベント会場の座席管理にも当てはまるため、将来的には店舗・施設向け（toB）の応用展開も見据えている。

## 2. このアイデアはどこから生まれたか

### 2-1. きっかけとなった体験・感情

RUNTEQの受講生グループでセルフカフェを使ったもくもく会を開催していたとき、毎回「みんながどのあたりに座っているか」が入室前にわからず、店内で探し回る場面が何度もあった。
ある日、グループとは関係ない別のお客さんに声をかけてしまい、気まずい思いをした。その瞬間、「入室前にみんながどこにいるか確認できれば、こんな思いをしなくて済むのに」と強く感じた。

また、飲食店やカフェのホール業務でも同様の課題があることを知った。混雑時に「どのテーブルが空いているか」「あのお客様はどこにいるか」をスタッフ間で共有するのに口頭確認やホワイトボードへの手書きで対応しており、ピーク時に情報が食い違い、案内ミスや二重案内が発生するケースがある。これは自分自身の課題ではないが、「誰がどこにいるかをリアルタイムで共有できない」という同じ構造の課題が業務現場にも存在することを知り、個人向けに作る仕組みが将来的に応用できる可能性があると気づいた。

### 2-2. なぜそれが「気になった」のか

以前に入室・退室の記録ができる出席管理アプリを自作した経験があり、「人の所在を管理する仕組み」への関心がもともと高かった。
その経験から「記録できること」の価値は知っていたが、もくもく会での体験で「直感的に・ビジュアルで・リアルタイムに」所在を共有できることの重要性を改めて実感した。
また、勉強会という特定の用途にとどまらず、会議室・教室・サークル活動など個人・カジュアルな集まり全般で使える汎用的な仕組みとして形にしたいと思ったことも動機のひとつ。将来的には同じ仕組みを業務現場（飲食店・イベント会場など）にも応用展開したいと考えている。
「仕組みで解決できることは仕組みで解決すべき」という価値観から、同じ情報を何度も人が確認・共有する手間を減らしたいという思いが強い。

## 3. 課題の整理

### 3-1. 表に見えている困りごと

もくもく会などのグループ集まりで入室前にメンバーの席がわからない。同様の構造の課題は飲食店・イベント会場などの現場でのスタッフ間の座席情報共有にも見られる。

### 3-2. 本当に解決したい課題は何か

**【主対象：カジュアルな集まり（toC）】**
- **なぜ困る？** → 入室しても誰がどこにいるかわからず、探し回ったり関係ない人に声をかけてしまう
- **なぜ困る？** → 気まずい思いをしたり、合流までの無駄な時間・ストレスが発生する
- **なぜ困る？** → 「自分がグループに合流できているか」という不安が、その場への参加ハードルを上げてしまう

**【将来的な応用先：業務現場（toB）】**
- **なぜ困る？** → 空席を即座に確認できないので、お客様をすぐ案内できない
- **なぜ困る？** → 案内が遅れると顧客満足度が下がり、スタッフ間の情報食い違いで二重案内・ミスが発生する
- **なぜ困る？** → スタッフの精神的負荷と業務ミスが増え、サービス品質全体が低下する

→ **本当に解決したい課題：所在情報がリアルタイムで共有されないことで、個人の集まりにおいて余計なストレス・合流の手間が生まれること（同じ構造の課題は業務現場にも存在し、将来的な応用先となる）**

## 4. 想定ユーザーについて

### 4-1. 想定しているユーザー

**年齢設定**
- 年齢：20〜40代。勉強会・もくもく会・サークル活動などに参加する個人ユーザーを主対象とする
- 理由：スマートフォン・タブレットを日常的に使いこなす世代であり、新しいWebツールへの抵抗感が低い

**生活・状況設定**
- 状況①（主対象・カジュアル）：週1〜複数回、カフェや共用スペースでグループもくもく会・勉強会・サークル活動を開催している個人
- 状況②（将来的な応用先・業務）：飲食店・ホテルロビー・コワーキングスペース・イベント会場などで座席・テーブル管理を担当するスタッフ・運営責任者
- 理由：どちらも「自由席の空間で、誰がどこにいるかが常に変わる」という共通の課題構造を持っており、同じ仕組みを応用できる

**環境設定**
- 環境：参加者が各自スマートフォンやタブレットを持ち、入室前・移動中にもアクセスできる
- 理由：「入室前に確認する」という使い方が核心であり、インストール不要のWeb完結型であることが重要

### 4-2. 自分とユーザーの距離

**過去の自分・現在の自分（主対象：カジュアル用途）**
RUNTEQのもくもく会で実際に気まずい体験をした当事者であり、課題の解像度が非常に高い。また出席管理アプリの開発経験があるため、「何が足りなかったか」を技術的にも体験的にも理解している。

**身近な誰か（将来的な応用先：業務用途）**
飲食・サービス業に携わる知人・友人の現場経験から課題を観察・共感しており、口頭確認やホワイトボード運用の非効率さへの理解がある。toC向けに磨いた仕組みを将来的に転用できると考えている。

### 4-3. 実際に使われる可能性について

- **最初に使ってくれそうな人：** RUNTEQの同期・もくもく会の主催者
- **思い出す場面：** もくもく会の開始直前、「今日みんなどこにいる？」とSlackで聞こうとした瞬間
- **今の代替手段：** Slackで「どこにいる？」と聞く・目視で探す
- **置き換える理由：** リアルタイム同期・複数端末での閲覧という、アナログ手段では実現できない価値がある。操作は「席をクリックして名前を入力するだけ」で、代替手段より明らかに速くストレスがない
- **（将来的な応用先：業務利用の場合）：** 混雑ピーク時に案内ミスが起きた直後、または新店舗立ち上げ時のオペレーション設計中に、ホワイトボード・紙の座席表・口頭確認からの置き換え先として検討されうる

### 4-4. 導入・継続の流れ

**【主対象：カジュアル用途】**
- きっかけ：もくもく会の主催者が「毎回どこにいるか確認が大変」と感じたタイミングで導入
- 最初の一歩：よく使うカフェのレイアウトを部屋エディタで作成 → フロアページのURLをグループのSlack・LINEに共有
- 使い続ける理由：「集まる前にURLを開いて席を登録する」という習慣が生まれ、使わないと逆に不便になる

**【将来的な応用先：業務用途】**
- きっかけ：繁忙期の案内ミス・スタッフ間の情報食い違いが続いたタイミングで「何かツールはないか」と検索
- 最初の一歩：自店のフロア図を部屋エディタで作成（5〜10分）→ フロアページURLをスタッフのスマホに共有するだけで即日運用開始
- 使い続ける理由：毎営業日の着席管理に使うことで習慣化。匿名化・集計済みの着席履歴データが蓄積し、混雑時間帯の分析や座席レイアウト改善の判断材料にもなる

**業務利用を見据える場合の観点（将来展望）：**
- 初期設定5分・インストール不要で導入コストが極めて低い
- 個人情報の取得を最小限に抑えるため、来店者には本名でなく**ニックネーム（任意の表示名）**の入力を案内し、データセキュリティ・個人情報保護のハードルを低くする
- 着席履歴の生データ（誰がいつ着席したか）は一定期間（例：当日中）で自動削除し、分析用途には集計済み・匿名化された統計データのみを残す
- 既存のPOSや予約システムとは競合せず「フロアの今を可視化する補完ツール」として乗り換えではなく追加導入しやすい

## 5. 既存サービス・競合調査

### 5-1. 似たサービスの調査

- **サービス名：** TableCheck（テーブルチェック）
- **URL：** https://www.tablecheck.com/ja/
- **できること：** 飲食店向け予約・顧客管理・フロアマップ管理。テーブルの着席状況をビジュアルで管理できる

### 5-2. それでも作りたい理由

TableCheckは飲食店の予約・CRM管理を主目的とした有料SaaSであり、業務利用が前提のため、「仲間内のもくもく会」「社内の会議室」「学校の教室」といった個人・カジュアルな用途には機能過多でコストも見合わない。
個人が「今日だけ使いたいレイアウトを5分で作ってすぐ共有する」という即興性・手軽さを求めるユースケースに応える既存サービスはなく、そこへの不満と「自分で作れる」という確信が作りたい理由の核心。将来的に業務現場への応用を考えた場合も、同じ仕組みを横展開できる汎用性を最初から持たせておきたい。

### 5-3. 差別化を一文で決める

**「勉強会・もくもく会・サークル活動など、カジュアルな集まりの場で入室前に全員の居場所をすぐ把握したい個人」の「合流の直前の確認の瞬間」を一番助けるアプリ**

## 7. このアプリで実現すること

### MVPで作る機能

- 部屋の新規作成（名前・幅・高さ）
- SVGキャンバスで壁（線分）・座席を描画・配置・保存
- フロアページでの着席・離席・席移動
- ActionCableによるリアルタイム同期（複数端末対応）
- 非ログインユーザー対応（URLでのアクセス・セッション管理）
- ルーム権限管理（編集権限の付与・剥奪）
- 複数フロア（部屋）の切り替え表示
- 認証機能（Devise によるユーザー管理）
- ロールベース権限管理（user, manager, admin）
- 自動離席機能・着席時間の管理（auto_checkout_at）
- 通知システム（チェックイン/チェックアウト通知、既読/未読管理）
- 変更履歴・監査ログ（PaperTrail による記録）

#### 部分実装・検討中分
- 着席履歴の詳細表示・CSV出力
- 座席ごとのメモ・タグ設定（禁煙席・VIP席・スタッフ専用など）
- スマートフォン向けUIの最適化
- よく使うレイアウトのテンプレート機能（カフェ・会議室・教室・ホテルロビーなど）
- 2要素認証（two_factor_controller）
- ユーザー招待機能（メール招待・トークンベース・7日間有効）
- バックアップ機能（S3 へのアップロード・自動・手動バックアップ）
- バックグラウンドジョブ（Sidekiq による非同期通知配信）

### 7-1. ログイン状態ごとの利用可能機能

参加者・お客様側の導入ハードルを下げるため、着席・離席のみは非ログインでも可能とし、それ以外の操作（上面図作成・権限管理など）はログインを必須とする設計。

| 機能 | 非ログイン | ログイン |
|---|---|---|
| 着席 | ○（着席時にニックネーム＝任意の表示名の入力が必要。本名の入力は推奨しない） | ○（ニックネーム入力不要） |
| 離席 | ○ | ○ |
| 上面図（部屋レイアウト）の作成 | × | ○ |
| 着席者の強制離席 | × | ○（上面図の作成者は常に可能。加えて作成者からロールを付与されたユーザーも可能） |

**ロール・権限の補足：**
- 上面図の作成者は、ロール付与の有無に関わらず常に着席者を強制離席させることができる。
- 上面図の作成者は、ほかのログインユーザーにロールを付与できる。
- ロールを付与されたユーザーは、作成者本人でなくても、着席中の人を強制離席させることができる。
- つまり「強制離席」の権限は作成者にデフォルトで備わっており、ロールという形で他のログインユーザーにも委譲できる。
- 誤操作・悪用時の説明責任を果たすため、「誰が」「いつ」「誰を」強制離席させたかをPaperTrailの監査ログに記録する。

### 7-2. プライバシー・データ取扱いに関する設計方針

- **表示名のみを取得：** 着席時に取得するのは本名でなくニックネーム（任意の表示名）。本名入力は推奨しない旨をUI上で案内する。
- **表示範囲の限定：** ニックネーム・着席状況は、対象の部屋（フロア）のURLにアクセスしている人にのみ表示する。検索エンジンへのインデックスはnoindex設定で防止し、不特定多数への公開は行わない。
- **保存期間の限定：** 個人を特定できる着席履歴の生データ（誰がいつ着席したか）は一定期間（例：当日中）で自動削除する。混雑時間帯の分析など長期的な活用は、個人を特定できない形に集計・匿名化したデータのみを保持する。
- **業務利用（toB）における表示の簡略化：** 飲食店・イベント会場などでの利用時は、来客個人のニックネームではなく「テーブルA：着席中」のような状態表示のみとし、来客の個人情報そのものを扱わない設計を選択できるようにする。
- **規約・ポリシーの整備：** 利用規約・プライバシーポリシー（取得する情報・利用目的・保存期間・第三者提供の有無）をサービス内に明示する。

## 8. 懸念点とその対策

### 懸念点① 自分から使い始めてもらえるか（初期利用のハードル）

- **問題：** グループ全員・スタッフ全員が使わないと価値が出ないサービスのため、主催者・管理者が導入しても参加者・スタッフが着席登録をしてくれない可能性がある
- **理由：** 新しいツールへの登録・操作を面倒に感じる人がいると、所在情報が不完全になりアプリの価値が半減する
- **対策：** アカウント登録不要でURLを開くだけで着席できる設計にする。操作は「席をクリックして名前を入力するだけ」にとどめ、参加者・スタッフの導入コストを極限まで下げる

### 懸念点② SVGエディタのモバイル対応

- **問題：** SVGのドラッグ操作がタッチデバイスで直感的に動かない可能性がある
- **理由：** タッチイベントとマウスイベントは別途対応が必要で、実装コストが高い
- **対策：** MVPではPCブラウザでのエディタ操作を前提とし、フロアページ（着席管理）のみスマートフォン対応を優先する

### 懸念点③ リアルタイム同期の接続安定性

- **問題：** ActionCableのWebSocket接続が不安定な環境（公衆Wi-Fi・モバイル回線）では同期が遅延・切断する可能性がある
- **理由：** カフェ・店舗現場ではネットワーク環境が安定していないケースが多い
- **対策：**
 - Redis接続失敗時に graceful に処理し、フォールバック機能を実装
 - ActionCableの接続状態を監視し、切断時に自動再接続
 - 座席操作時の状態保存により、オフライン状態でも動作を継続
 - 再接続後に最新状態をREST APIでフェッチして画面を復元

### 懸念点④ 個人情報保護法・プライバシーへの対応

- **問題：** 着席時に入力される名前や着席履歴は、個人を識別できる情報（個人情報）に該当しうる。本名入力や履歴の長期蓄積、不特定多数への表示が行われると、個人情報保護法上の利用目的の明示義務やプライバシー侵害のリスクが生じる
- **理由：** 「誰がどこにいるか」を可視化するサービスの性質上、個人の所在情報を扱うこと自体が前提となっているため、設計を誤ると個人情報・プライバシーへの配慮が不十分になりやすい
- **対策：**
 - 本名でなくニックネーム（任意の表示名）の入力を案内し、取得する情報を最小限にする
 - ニックネーム・着席状況の表示範囲を、対象の部屋にアクセスしている人のみに限定する
 - 個人を特定できる着席履歴の生データは短期間（例：当日中）で自動削除し、長期保持するのは匿名化・集計済みのデータのみとする
 - 業務利用（toB）では来客個人の表示名を出さず、「テーブルA：着席中」のような状態表示のみにする選択肢を用意する
 - 利用規約・プライバシーポリシーをサービス内に明示し、取得する情報・利用目的・保存期間を案内する
 - 強制離席など他者に影響する操作は、PaperTrailで「誰が・いつ・誰に対して」行ったかを記録し、トラブル時の説明責任を果たせるようにする

## 9. 今後の展開・発展の方向性

### 観点

- **使い続ける理由：** 毎回の集まりで「URLを開いて席を登録する」が習慣化されると、使わないと逆に不便になる
- **データが溜まると：** 変更履歴（PaperTrail）・自動離席記録により、よく使われる座席・時間帯が可視化でき、レイアウト改善の判断材料になる
- **通知機能による運用効率化：** チェックイン/チェックアウト通知により、リアルタイムの着席状況が全員に共有される
- **複数ユーザー管理：** 招待機能・ロールベース権限管理により、グループ内での協業が実現

### 今考えている発展案（toC：主対象の発展）

## 10. 技術スタック

### 10-1. 使用予定の技術

- **バックエンド：** Ruby on Rails 8.1.3
- **フロントエンド：** React 18+ / Inertia.js
- **フロント構築：** Vite + `vite_ruby` / Tailwind CSS v4
- **DB：** PostgreSQL
- **リアルタイム：** ActionCable (WebSocket) + Redis
- **認証：** Devise + 2要素認証
- **権限管理：** Pundit（ポリシーベース）
- **バックグラウンドジョブ：** Sidekiq
- **監査ログ：** PaperTrail
- **ストレージ：** AWS S3（バックアップ用）
- **デプロイ先：** Render.com（Web Service + PostgreSQL）

#### 主要ライブラリ
 - `inertia_rails`（Rails↔React橋渡し）
 - `vite_ruby` + `@vitejs/plugin-react`（フロントエンドビルド）
 - Tailwind CSS v4
 - `@rails/actioncable`（WebSocketクライアント）
 - `devise`（ユーザー認証）
 - `pundit`（権限管理）
 - `sidekiq`（バックグラウンドジョブ）
 - `paper_trail`（監査ログ）
 - `aws-sdk-s3`（バックアップストレージ）
 - `ransack`（検索・フィルタリング）
 - `kaminari`（ページネーション）

### 10-2. 技術選定の理由

- **Rails：** 業務ロジック・DBまわりを素早く実装でき、ActionCableが標準搭載のためリアルタイム機能を追加コストなく実現できる
- **Inertia.js：** APIを別途設計せずRailsのコントローラーからReactコンポーネントに直接データを渡せるため、小規模アプリに適している
- **React + SVG直書き：** 外部グラフィクスライブラリに依存せず、座席・壁をSVG要素として直接操作することでドラッグ処理を完全にコントロールできる
- **Devise + Pundit：** Rails スタンダードの認証・権限管理で、セキュアかつメンテナンス性の高い実装が可能
- **Sidekiq：** バックグラウンドで通知配信・バックアップ作成などの重い処理を非同期実行
- **PaperTrail：** 変更履歴・監査ログを自動記録し、コンプライアンス・デバッグに活用
- **AWS S3：** データベースバックアップを定期的に外部ストレージに保存し、災害対策を実現

### 10-3. 実装での工夫

- **SVGのインタラクション実装：** 複数座席の範囲選択（マルチ要素選択ツール）を実装し、操作効率を向上
- **Redis 接続の安定性：** Redis 接続失敗時に graceful に処理し、フォールバック機能を実装
- **非同期通知：** Sidekiq による非同期通知配信で、UI の応答性を保証
- **権限管理：** Pundit ポリシーを使用した細粒度の権限制御（ルーム所有者・権限ユーザー・一般ユーザー）

### 10-4. キャッチアップと開発経験

以前の出席管理アプリ開発経験から、入退室の記録・状態管理の設計については知見がある。その土台を活かしつつ、SVGエディタ・リアルタイム同期・複数ユーザー権限管理といった新要素に集中してキャッチアップした。
ActionCable と React 状態管理の連携、SVG のドラッグ操作など、複雑なフロントエンド実装も段階的に実装・検証を進めることで、安定動作を実現。
